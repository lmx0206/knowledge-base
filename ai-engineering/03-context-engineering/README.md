# 上下文工程 (Context Engineering)

> 阶段：2025（第二代）
> 核心问题：在正确的时刻，给 AI 正确的信息
> 提出者：Andrej Karpathy 等人

## 什么是上下文工程？

上下文工程是**有意识地设计和管理 AI 上下文窗口中内容**的学科 —
包括放什么进去、什么时候放、以什么格式放。

> "上下文工程比提示词工程重要得多。" — Andrej Karpathy, 2025

## 为什么比提示词工程重要？

```
提示词工程：写好一个问题
上下文工程：确保 AI 在回答前看到了所有它需要的信息

比喻：
  提示词 = 你问医生的问题
  上下文 = 你给医生看的病历、检查报告、用药记录
```

即使是最强的模型，没有正确的上下文也会"瞎猜"。
而一个弱模型，有了充足的上下文，也能做出准确判断。

## 六大核心技术

### 1. 系统提示 (System Prompt)

定义 AI 的身份、规则和行为边界：

```markdown
你是一个 Android 开发助手。
规则：
- 优先使用 Kotlin 而非 Java
- 遵循 MVVM 架构
- 使用 Jetpack Compose 而非 XML 布局
```

### 2. RAG（检索增强生成）

根据用户问题，动态检索相关文档注入上下文：

```
用户问题："如何在 Compose 中实现懒加载？"
      ↓ 检索
注入上下文：LazyColumn 文档 + 项目中的示例代码
      ↓
AI 基于实际文档回答，而非"记忆"
```

### 3. 记忆系统 (Memory)

```
短期记忆：当前对话的上下文
长期记忆：跨会话的用户偏好、项目信息
工作记忆：当前任务的状态和进度
```

### 4. 工具定义 (Tool Definitions)

告诉 AI 它能用什么工具：

```json
{
  "name": "search_files",
  "description": "搜索文件内容",
  "parameters": {
    "pattern": "搜索模式",
    "path": "搜索路径"
  }
}
```

### 5. 上下文压缩 (Compaction)

当上下文太长时，智能压缩保留关键信息：

```
原始对话（5000 tokens）
    ↓ 压缩
摘要（500 tokens）+ 关键事实 + 待办事项
```

### 6. 上下文窗口管理

```
决定：
- 什么信息应该保留？
- 什么信息应该丢弃？
- 什么信息应该总结？
- 什么信息应该按需检索？
```

## 实践框架

### 上下文的四个维度

```
┌─────────────────────────────────────────┐
│           上下文窗口                      │
│                                         │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐ │
│  │ 系统指令 │  │ 工具定义 │  │ 记忆    │ │
│  │ (固定)   │  │ (固定)   │  │ (动态)  │ │
│  └─────────┘  └─────────┘  └─────────┘ │
│                                         │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐ │
│  │ 对话历史 │  │ RAG结果  │  │ 工具输出 │ │
│  │ (滚动)   │  │ (按需)   │  │ (按需)  │ │
│  └─────────┘  └─────────┘  └─────────┘ │
└─────────────────────────────────────────┘
```

### 信息注入的时机

| 信息类型 | 何时注入 | 示例 |
|---------|---------|------|
| 系统指令 | 每次对话开始 | personality、rules |
| 项目规则 | 每次对话开始 | AGENTS.md |
| 用户记忆 | 每次对话开始 | MEMORY.md、USER.md |
| RAG 结果 | 用户提问时 | 相关文档片段 |
| 工具输出 | 工具调用后 | 搜索结果、文件内容 |
| 压缩摘要 | 上下文接近上限时 | 历史对话总结 |

## 在 Hermes 中的实现

| 上下文技术 | Hermes 功能 | 命令 |
|-----------|------------|------|
| 系统提示 | personality + system prompt | config.yaml |
| 项目规则 | AGENTS.md 自动注入 | 项目根目录放置 |
| 用户记忆 | Memory 系统 | memory 工具 |
| RAG | Skills 按需加载 | /skill name |
| 工具定义 | 工具集自动注册 | hermes tools |
| 上下文压缩 | 自动压缩 | compression 配置 |
| 历史搜索 | session_search | 跨会话检索 |

## 弱模型 + 好上下文 = 强表现

这是对你最重要的部分：

```
mimo-v2.5-pro（弱模型）+ 糟糕上下文 = 不可用
mimo-v2.5-pro（弱模型）+ 精心设计的上下文 = 可用且可靠

具体做法：
1. AGENTS.md → 告诉模型项目背景（不用它自己"猜"）
2. Memory → 告诉模型你的偏好（不用每次重复）
3. Skills → 给模型精确步骤（不用它自己"推理"）
4. RAG → 给模型参考资料（不用它靠"记忆"）
5. 工具调用 → 让模型用工具验证（不用它"相信自己"）
```
